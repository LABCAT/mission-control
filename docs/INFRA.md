## Preview lifecycle (`.github/workflows/preview.yml`)

Each preview is a Worker Preview plus a Neon branch `preview/<name>`. `<name>` comes from `.github/scripts/preview-name.sh`. Neon limits how many branches a project can have, so previews must not pile up (PJ-86).

| Event | What happens |
|---|---|
| Push to a branch with an open PR, or a PR is opened/reopened | Preview is published. The Neon branch is created once and kept, so test data survives later pushes. |
| Push to a branch with no open PR | Nothing. The `gate` job skips the preview. Opening the PR creates it. |
| Push after a PR re-created a migration | If the kept preview DB has an applied migration that is in neither the branch nor `origin/main`, the Neon branch is deleted and recut from prod before migrating (`preview-migrations.mjs`). Test data in that preview is lost. |
| Manual run with `reset_preview` (a git branch) | Deletes that one preview (Worker Preview and Neon branch) and re-runs the branch's latest push run to rebuild it. |
| RC tag | `preview/rc-<version>` is recreated from prod. `release.yml` deletes it on release. |
| PR closed or merged, or git branch deleted | `cleanup` job deletes that branch's Worker Preview and Neon branch, unless another open PR maps to the same preview name (`feature/foo` and `feature-foo` do). |
| Daily at 03:17 UTC, or manual | `sweep` job deletes every stale `preview/*` Neon branch and its Worker Preview. |
| Creating a branch would hit the limit | The job fails early and lists the existing `preview/*` branches. |

The branch limit defaults to 10. Set the repository variable `NEON_BRANCH_LIMIT` to match the Neon plan.

### The sweep

A preview is **stale** when no open PR from this repo has its branch name. The sweep never deletes:

- `main`, or any branch that isn't `preview/<name>`. The rule is strict: `preview/` followed by a lowercase DNS label of at most 40 characters.
- `preview/rc-*`. RC previews belong to the release flow.
- A branch Neon marks primary, default or protected.

It stops without deleting if the Neon list has no `main` or the open PR list could be truncated. The rules live in `.github/scripts/preview-neon.mjs` and are tested in `preview-neon.test.ts` (`pnpm test`). Every delete goes through `.github/scripts/delete-preview.sh`, which first checks the name with `preview-neon.mjs deletable` (a well-formed `preview/<name>` that is not `preview/rc-*`; a branch like `rc/0.2.0` maps to an RC name, so it is skipped with a notice). Right before deleting, it fetches the open PRs again and skips the preview if an open PR now maps to its name, so a PR opened during a sweep keeps its preview. It tolerates only a confirmed "not found" from the Worker Preview delete, and fails on any other error before touching Neon. It treats a Neon branch as absent only if the branch list was fetched and parsed successfully.

Manual runs default to a **dry run** that only lists what it would delete (also in the run summary). To clean up the current backlog, dry run first, then delete:

```bash
gh workflow run preview.yml --repo LABCAT/mission-control -f dry_run=true
gh workflow run preview.yml --repo LABCAT/mission-control -f dry_run=false
```

`workflow_dispatch` only works once this workflow is on `main`.

## R2 (media and documents)

The `media` and `documents` collections store files in the `mission-control-media` bucket through the `MEDIA` binding (`apps/cms/wrangler.jsonc`). Each upload gets its own folder, so keys look like `<uuid>/<filename>`. Documents are private (tenant members only); media is public-read.

- **Local dev and tests:** wrangler's local R2 (miniflare), no Cloudflare account needed. Tests use `getPlatformProxy` with an in-memory bucket.
- **Worker Previews** get no bindings, so previews have no `MEDIA` and uploads there are unavailable.
- **Image variants:** 320/640/960/1280 px, each as AVIF and WebP, are generated by sharp under Node only (CLI, tests, import scripts). sharp can't load in workerd, so uploads made in the production Worker keep the original only and leave the variant fields empty. Resizing inside the Worker needs the Cloudflare Images binding (billed per unique transformation after a free allowance); the founder deferred that to PJ-85 (1.x, decision of 18 Nov). Sites render the original `url` when an image has no variants.


### Resetting a preview (PJ-90)

The Neon branch of a preview is kept across pushes, so its database remembers every migration it has run. AGENTS.md tells agents to delete and re-create a migration when it needs redoing. The new file has a new timestamp but makes the same schema change, so `payload migrate` on the kept database fails with "column already exists".

Before migrating, the Publish job reads `payload_migrations` from the preview database and compares it with `apps/cms/src/migrations` and with `origin/main` (what prod has, so a PR that is behind main does not reset on every push). Any applied name found in neither means the database is stale, so the job resets it. It never does this for `preview/rc-*`, a fresh RC copy, or any branch that is not `preview/<name>`. The decision lives in `.github/scripts/preview-migrations.mjs`, tested in `preview-migrations.test.ts`.

To reset one preview by hand (for example one stuck with bad data), pass its **git branch** (`feature/foo`), not the preview name (`feature-foo`). The branch must exist, and this is checked before anything is deleted. This deletes its Worker Preview and Neon branch and re-runs the branch's latest push run, which builds both again:

```bash
gh workflow run preview.yml --repo LABCAT/mission-control -f reset_preview=openhands/pj-17-locations-tree
```

It uses the same guards as the sweep (`delete-preview.sh`: never `main`, never `preview/rc-*`), except that it skips the "an open PR uses this preview" check, since resetting a live PR's preview is the point. When `reset_preview` is set, the run resets that preview and does not sweep.
